MySchool ERP

A Django ERP for schools and colleges, used every day at MySchool Jhang for admissions, exams, fees, finance, staff and parents.

Problem

The school ran on registers, paper fee receipts and spreadsheets. It needed one system for admissions, exams, fees and staff, with result cards, receipts and certificates printed from the same data, and a way for parents to see fees, attendance and results themselves.

Users

Administrators, the principal, teachers, accountants, parents and admission applicants — each with their own login and permissions.

My role

I gathered requirements with school staff, then designed, built, deployed and maintain the system: data model, screens, PDF documents, permissions, tests and the server. I use AI coding assistants in my workflow and review and test everything that ships.

Implemented features

  • Admissions: student records, online applications with documents and fee challan, entrance test (timed, with tab-switch control), merit list and enrolment.
  • Exams: marks entry, real-time result cards as PDF (one student or a whole class), school leaving certificates.
  • Assessment: question bank, paper builder, daily tests, and online exams for students who are away.
  • Teaching content: 277 printable A4 lesson worksheets for Oxford Progressive English Books 1–5, each in three levels with answer keys and an audio QR code for parents.
  • Fees and finance: fee vouchers, family fee, bank-list import, defaulter lists, chart of accounts, double-entry vouchers, trial balance and profit and loss, month-end locks.
  • Staff: HR records, departments, salary structures, payroll and attendance.
  • Parents: an installable web app (PWA) with results, attendance, fees and homework diary; WhatsApp report links.
  • AI (Claude API): a school assistant chatbot that answers questions from live school data, and a fee-reminder assistant that drafts a personal message per defaulter and prepares a WhatsApp link for a person to send.

Architecture decisions

  • Feature plans instead of forks. A feature registry and middleware switch whole modules on or off per institution (Basic, Standard, Premium). A school can upgrade later without migrating data.
  • Offline installs with a signed licence. For schools without reliable internet, the same code runs on a local computer and checks a cryptographically signed licence key.
  • One codebase, several institutions. Each server reads its own private settings file (secret key, database, plan), so a second institution runs the same code with its own data.
  • Server-rendered Django. Pages are rendered on the server with small amounts of JavaScript, which keeps the system fast on low-end phones and simple to maintain.
  • PDFs generated in Python. Result cards, certificates, vouchers and worksheets are produced with ReportLab, including Urdu text shaping.

Security and data handling

  • Role-based access for every screen; the principal’s role is read-only where it should be, enforced in middleware.
  • National identity (CNIC) numbers validated to one 13-digit format everywhere, with a data migration that cleaned existing records.
  • Secrets and database settings live in a private environment file; debug mode is off by default.
  • Finance months can be locked, and changes to the books are audited.
  • The live system holds children’s records, so public material uses sample data only and no live address or login is published.

Challenges and lessons

  • Messy real-world data. CNIC numbers had been typed in several formats on different screens. A single shared field plus a migration that tidied old records fixed it once, instead of patching each screen.
  • Different institutions want different things. Building feature plans early avoided maintaining separate copies of the code for each customer.
  • Content at scale needs checks. The 277 worksheets are written in a small Python format and checked automatically for A4 fit and complete answer keys before they reach teachers.
  • AI should draft, people should decide. The fee assistant drafts messages but never sends them; a staff member reviews and sends each one.

Evidence

36 automated tests pass on the current code. The demo video and brochure use sample data. Source code is private because the system runs a real school; a walkthrough on a demo database is available on request.
